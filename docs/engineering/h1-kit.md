# H1 Kit Standard (executable acceptance packages)

Single canonical rule set for producing owner-H1 acceptance artifacts
anywhere in the Qiven workspace (Devkit-canonical per ADR-0046; born
2026-09-23 from the MVP-4 deny-118 incident — owner direction: an H1
kit as a prose document the owner must interpret was declared a defect
class). Companion ADR: qiven-context ADR-0049 (proposed).

## 1. What an H1 kit IS

An H1 acceptance point means THE OWNER'S HANDS run a prepared, complete,
self-rollback-able PACKAGE — like a deployment, but through the H1
acceptance path instead of the deploy path. A kit is therefore:

1. **Built by a tool** (the repository's `tools/h1_kit.py` class), never
   hand-assembled by a session; the tool enforces deploy-grade
   preconditions (clean tree at an exact head with a gate PASS receipt).
2. **Complete**: every artifact the owner needs is in the package —
   binaries to run, the exact configuration files to install (no owner
   authoring, no "add this to your config" prose), double-clickable
   launchers, evidence collectors, a rollback script, and the operation
   guide.
3. **Single-sourced**: the guide, probes, and rubric are GENERATED by
   the tool. A prose copy in `docs/` is a POINTER to the kit, never a
   second statement of the steps (drift between doc and package is the
   original defect).
4. **Enable-gated**: installing configuration that affects the owner's
   live environment (workspace client configs) has NO live effect until
   the owner approves it in that environment's UI review — the session
   may write the file; only the owner's review arms it.
5. **Rollback-able**: the tool backs up every file it replaces, and the
   rollback script restores it without interpretation.

## 2. Owner-facing content law (hard rules)

1. **GUIDE.md is the entry point**, numbered steps, each step states the
   EXACT UI action or file path (absolute paths) — "review and approve
   the changed hook configuration in Settings → Hooks", not "attach the
   hooks".
2. **Commands are shell-labeled and shell-correct.** Every inline
   command block names its shell (cmd / PowerShell / Git Bash) and uses
   that shell's path syntax — `cd /d D:\x` (cmd), `cd D:\x` /
   `cd /d/x` (Git Bash). A command the owner's shell cannot execute is
   a kit defect (the `cd D:\JasonWork\qiven-runtime`-in-Git-Bash class,
   observed 2026-09-23). Prefer double-clickable launchers so the owner
   types nothing.
3. **Copy-paste payloads are complete**: probe prompts, relay messages,
   and anything the owner must transmit are given verbatim, one block
   each.
4. **Human-facing output law applies inside the kit's binaries**: a
   console the owner watches prints staged `[ RUN]/[ OK]/[FAIL]` output,
   names every durable path it writes, and heartbeats during healthy
   silence. A silently-running tool is a defect even when correct.

## 3. Trust and evidence

- Identity that governs behavior (event kinds, tool names, session
  tokens) comes from the REGISTRATION TEMPLATE the kit pins — never
  from harness payload fields, which are corroborating evidence only
  (the deny-118 root cause: a REQUIRED assumed payload field).
- Unverified external contracts (harness payloads, foreign schemas) are
  probed BEFORE enforcement: kits carry a capture step (e.g.
  `--dump-stdin`) so real-world shapes become recorded evidence, and
  fail-closed defaults never ship as REQUIRED assumptions.
- The manifest binds every file's digest to the exact validated head;
  the sealed evidence the owner relays back is graded against the rubric
  the kit itself shipped.

## 4. Kit layout (normative minimum)

```text
<kit>/ GUIDE.md  manifest.json  config.json  config.pre-<trial>.json
       bin/  run-*.cmd  stop-*.cmd  collect-evidence.cmd  rollback.cmd
```

Repositories may extend it; they may not drop the minimum.
